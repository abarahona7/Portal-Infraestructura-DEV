# Tablero de activos TI en DEV

La sección «Equipos → Tablero de Activos» resume el maestro completo de `Equipamiento`, incluidos los activos anteriores al módulo ITAM. Muestra total, disponibles, asignados, en reparación, en préstamo y dados de baja; también identifica activos sin serie, sin activo fijo y con custodio no activo. Estos últimos se muestran con el estado exacto del colaborador, una lista paginada y acceso al historial del equipo; el tablero no modifica asignaciones automáticamente. La revisión técnica cuenta celulares sin IMEI y Notebook/Mac sin Hostname o MAC, excluyendo los dados de baja. Un equipo con varios faltantes se cuenta una sola vez en el total de fichas incompletas. Se muestran inicialmente los diez registros pendientes más recientes; «Ver todos» abre una lista paginada con acceso al formulario de edición de cada ficha. Las distribuciones por tipo, ubicación y área asignada presentan las diez categorías principales más «Otros». Los últimos ocho movimientos muestran folio y permiten abrir el historial o descargar el acta.

`GET /api/activos/resumen/` calcula los indicadores en MySQL y requiere el mismo rol de lectura de Equipos (Operador Infraestructura o Administrador). No crea ni modifica registros. El navegador solicita los datos al abrir el tablero o al pulsar «Actualizar», y la respuesta usa `Cache-Control: no-store`. `GET /api/activos/pendientes-tecnicos/?page=1&page_size=20` permite recorrer todas las fichas incompletas. `GET /api/activos/custodios-no-activos/?page=1&page_size=20` lista los equipos cuyo custodio está en LICENCIA, BAJA o sin estado activo, sin entregar RUT ni correo. Ambos endpoints usan los mismos permisos y evitan caché. El tablero se carga bajo demanda para no aumentar la descarga inicial del portal. El contador de movimientos de los últimos 30 días empieza con la nueva trazabilidad: no reconstruye documentos ni movimientos antiguos.

El bloque «Reporte de movimientos» permite descargar un CSV UTF-8 filtrado por fecha inicial, fecha final y tipo (`GET /api/movimientos/reporte/`). Sin filtros incluye todos los movimientos ITAM registrados y conserva el orden más reciente primero. El reporte contiene identificadores, fecha, tipo, custodios, ubicaciones, estado resultante y folio; no incluye RUT, correo, observaciones, snapshots completos ni PDF. Las columnas de equipo, serie y activo fijo reflejan la ficha actual del activo; para constancia histórica inmutable se debe consultar el acta asociada. El servidor valida fechas y tipos, usa los mismos permisos del historial (Operador Infraestructura o Administrador), evita caché y protege las celdas de texto que podrían interpretarse como fórmulas en una planilla. La descarga se transmite por bloques para evitar construir el archivo completo en memoria.

No se requiere migración ni infraestructura QA para estos indicadores. Los respaldos previos están en `.local/backups/portalinfra_dev_backup_pre_itam_calidad_20260930_030732.sql`, `.local/backups/portalinfra_dev_backup_pre_itam_paginacion_tecnica_20260930_031703.sql`, `.local/backups/portalinfra_dev_backup_pre_itam_custodios_no_activos_20260930_122505.sql` y `.local/backups/portalinfra_dev_backup_pre_itam_reporte_movimientos_20260930_125209.sql`. En DEV se verificó con `python manage.py shell < scripts/validar_dashboard_itam.py`, que crea datos temporales dentro de una transacción, comprueba conteos, distribuciones y permisos, y revierte todo. El reporte se verificó con `python manage.py shell < scripts/validar_reporte_movimientos_itam.py`, incluyendo filtros, roles y escape de fórmulas con el mismo rollback. Para la comprobación general: `python manage.py validar_integridad_portal`, `npm run lint` y `npm run build` desde `siminfra-frontend`.

El seguimiento visual de garantías opcionales se describe en [ITAM_GARANTIAS_DEV.md](ITAM_GARANTIAS_DEV.md). La validación en QA se hará cuando exista el ambiente y se gestione acceso al servidor y la aplicación.
